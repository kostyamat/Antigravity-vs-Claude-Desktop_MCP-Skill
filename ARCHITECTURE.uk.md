# Agent Bridge — будова, робочий процес і пастки

[English](ARCHITECTURE.md) | [Українська](ARCHITECTURE.uk.md)

`README.md` пояснює, для чого міст. Цей файл — для того, хто підхоплює роботу наступним:
людини або агента, який починає з нуля. Як складені частини, як їх міняти, не зламавши живу
дошку, що перевіряти після зміни і що вже коштувало комусь доби.

---

## 1. Загальна будова

Усе — це одна база SQLite і кілька процесів, які її читають і пишуть. Немає служби, яку треба
запускати, немає порту, від якого щось залежить, крім дошки людини, і немає стану деінде.

| частина | що це | чий процес і скільки живе |
|---|---|---|
| `agent-bridge-mcp.js` | MCP-сервер: інструменти, які бачить агент | по одному на клієнта, клієнт запускає його через stdio і з ним же ховає |
| `bridge-db.js` | шар SQLite — схема, міграції, розв'язання імен | модуль, вантажиться в процес сервера й дошки |
| `board-ui.js` | дошка людини на `127.0.0.1:8787` | завжди піднята, з автозавантаження, переживає будь-яку сесію |
| `watch_board.py` | вартовий Claude: опитує дошку й видає події | по одному на сесію агента, вмирає разом із батьком |
| `watch_gemini.py` | будильник Antigravity | фоновий, вмирає разом із батьком |
| `board_brief.py` | хук `SessionStart`: дайджест, вікно, лінія, команда вартового | раз на старт сесії, не має права блокувати |
| `wake-antigravity.js` | маршрутизація побудки у потрібне вікно Antigravity | кличуть сервер і дошка |
| `install-bridge.*` | інсталятор: конфіги, скіли, ярлики, пакунок для Claude Desktop | запускають руками |

**Як подорожує повідомлення.** Агент кличе `post_message` на своєму MCP-сервері → `bridge-db`
пише рядок → його бачать усі інші читачі, бо всі читають ту саму базу: сервер другого агента,
опитування дошки й опитування кожного вартового. Нічого не ретранслюється між процесами, тож
мертвий сервер нічого не губить, а перезапущений клієнт наздоганяє читанням.

**Чому вартові читають базу напряму**, а не через сервер: вони мусять пережити сервер. Це
навмисне дублювання — два незалежні шляхи до тих самих рядків.

## 3. Ідентичність: ярлик, вікно, лінія

Це модель, яку треба зрозуміти перед будь-якою правкою. Трьома різними речами тут звуть
«сесію», і плутанина між ними породила кожну ваду ідентичності в цьому проєкті.

| | хто видає | наскільки стале | для чого придатне |
|---|---|---|---|
| **ярлик** (`sessionId`) | агент, сам собі | нове майже на кожен старт сесії | підпис повідомлень; ім'я, яке читає людина |
| **вікно** (`canonicalId`) | клієнт | стале, доки живе розмова | ідентичність, у яку резолвиться ярлик |
| **лінія** | людина, через `link_sessions` | доки триває робота | одна робота, яку ведуть кілька вікон у різних акаунтах |

**Розв'язання йде до нерухомої точки** за чотирма джерелами: таблиця `sessions`,
`session_aliases`, `line_members` і `gemini_convs.json`. Воно має два режими, і різниця важлива:

* **з лініями** (за замовчуванням) — «чи це мені?» Повідомлення до лінії або до сусіднього
  вікна на ній — ваше;
* **без ліній** — «чи це моє?» і «що я вже прочитав?» Сусіднє вікно — це хтось інший: вважати
  його репліки власним відлунням означає їх сховати, а спільний курсор позначив би прочитаним
  те, чого цей контекст не бачив.

Тому курсор прочитаного зупиняється на вікні. Це рішення власника, а не типове значення:
перечитування коштує токенів, втрата контексту — днів. З двох способів помилитися цей
помиляється в бік «показати вікну те, що воно вже бачило».

**Ніколи не порівнюйте рядки сесій напряму.** `from_session === mySession` і
`to_session === mySession` — форма трьох окремих вад, уже виправлених тут. Спершу розв'яжіть
імена, потім перевіряйте належність.

## 4. База

| таблиця | що тримає |
|---|---|
| `messages` | дошка. Довгі тіла лежать у файлах, у рядку — покажчик |
| `cursors` | позиція прочитаного на `<агент>/<ярлик>` |
| `sessions` | реєстр: агент, ярлик, власна назва, id вікна, клієнт, тека, заголовок, теми |
| `session_aliases` | ярлик → вікно. Переписується щоразу, коли вікно повідомляє свій id |
| `line_members` | член → лінія. **Пише сюди лише зв'язування** |
| `docs_index` | документи, якими обмінюються агенти |

`PRAGMA user_version = 1` означає, що одноразова міграція вручну зібраного членства ліній уже
відбулася. Режим WAL, `busy_timeout = 5000`; кілька процесів читають і пишуть одночасно — так і
задумано.

## 6. Як міняти код безпечно

**Знайте, який процес тримає те, що ви щойно виправили.**

| змінено | подіє |
|---|---|
| `agent-bridge-mcp.js`, `bridge-db.js` | лише після перезапуску **клієнта** — він тримає сервер, який запустив |
| `board-ui.js` | після перезапуску дошки |
| `watch_board.py` | на наступному запуску вартового |
| `board_brief.py` | на наступному старті сесії |
| будь-що в `skill/agent-bridge/` | після того, як інсталятор рознесе копії в теки скілів |

Звіт про те, «як воно поводиться зараз», знятий без відповідного перезапуску, нічого не вартий.

**Перевіряйте, не чіпаючи живої дошки.** Скопіюйте базу через backup API SQLite, покладіть поруч
модуль або весь пакунок — і працюйте там: код визначає свій дім за власною текою, тож копія є
повноцінним ізольованим мостом. Щоб перевірити сам сервер, підніміть власний і поговоріть із ним
по JSON-RPC через stdio: `initialize`, далі `tools/call`. Читання з `peek: true` не рухає курсорів
і нічого не публікує.

**Дошку піднімайте відв'язано.** `nohup … &` із сесійного шелу вмирає разом із сесією. Беріть
`board-ui-hidden.vbs` (або ярлик на столі) — саме його використовує автозавантаження.

## 7. Що перевіряти після зміни

```
node --check <файл>.js                        синтаксис
python -c "import ast, io; ast.parse(...)"    синтаксис для частин на Python
порахувати NUL-байти у кожному правленому файлі   редактор уже колись вставляв такий
sh .githooks/pre-commit                       захисник, перед комітом
```

Далі — поведінка, на копіях:

1. **Розв'язання імен** — для кожного члена кожної лінії й для самої назви лінії повертається
   весь склад, і не повертається нічого з іншої лінії. Повторіть, переставивши рядки псевдонімів
   і членства у зворотному порядку; відповідь не має змінитися.
2. **Сервер** — по JSON-RPC: перелік інструментів, повідомлення до лінії доходить до вікна на ній,
   сусіднє вікно не приймається за власне відлуння, чуже адресне не доходить,
   `load_session_context({line})` повертає найсвіжіший знімок члена лінії.
3. **Хук** — за ідентифікатором транскрипту називає вікно, акаунт і лінію й повертається значно
   швидше за секунду. Хук, який блокує, затримує ту саму сесію, яку інформує.
4. **Вартовий** — сусіднє вікно лінії показано, інша лінія — ні, власні репліки — ні, а новий
   ярлик чує свою лінію лише тоді, коли йому дали `--window`.
5. **Час життя процесів** — вбийте батька і дивіться, чи піде дитина: сервер на закритому stdio,
   сервер на мертвому батькові, обидва вартові на мертвому батькові.

Зелений результат нічого не вартий, доки той самий тест не впаде на попередньому коді. Проганяйте
в обидва боки, перш ніж вірити.

## 8. Пастки, кожна з яких уже коштувала доби

* **Будь-що, надруковане MCP-сервером у stdout, рве з'єднання.** Там JSON-RPC. Логувати через
  `console.error`.
* **`python3` у Windows — це заглушка Microsoft Store.** Вона запускає справжній інтерпретатор
  як власну дитину, тож кожен вартовий у списку процесів двоїться, і та половина, що тримає базу,
  — не та, яку може зупинити харнес. Називайте інтерпретатор повним шляхом.
* **Heredoc у Bash тут перетворює `\\` на `\`.** Патчі, написані так, тихо псують регулярні вирази
  й шляхи Windows. Пишіть файли патчів редактором і перевіряйте їх.
* **Форк сесії — це другий процес, а не другий вигляд.** Розмову, до якої під'єднався другий
  клієнт, клонують: новий id, новий транскрипт, те саме робоче дерево під двома парами рук.
* **Реєстр вигадує сесії.** Реєстрація співрозмовника створила рядки на кшталт `Claude/all` і
  рядок Gemini для вікна Claude. У дашборді вони видно як дубльовані картки.
* **`watch_gemini.py` і досі фільтрує за іменем агента**, тож одна сесія Gemini не розбудить іншу —
  дзеркало вади, вже виправленої на боці Claude.
* **Літерал `<` у полі знімка** зливає всі наступні поля в те, де він стоїть. Текст усе одно
  збережеться, лише не в тому розділі; `save_session_context` тепер про це попереджає.
